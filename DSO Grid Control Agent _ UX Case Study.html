1. Executive summary and scorecard

The DSO Grid Control Agent and Command Centre is a desktop dashboard for a Distribution System Operator (DSO). One screen shows agent status and latency, feeder load, distributed energy resources (DER) that can be dispatched, AI decisions with their reasons, live events, an auditable log, history and a chat with the AI agent. It is built around a human-in-the-loop principle: the AI recommends and explains; the operator approves or overrides; every action is logged.

The design is shown in three themes (navy and sand, dark slate, and a light cream theme) with a sun and moon toggle. I have not reviewed earlier versions of this project in this conversation, so the assessment below covers the current state rather than a before-and-after comparison.

The strongest thing about this project is domain credibility: it uses real DSO concepts (feeders, DER, dispatch, audit logs, Beckn-style init and confirm messages). The biggest weakness is legibility: much of the text is very small and several colour pairs are below WCAG contrast, which matters for a control-room tool used for long shifts.

1.1 What has improved

  • Clear panel structure: header KPIs, then Feeder, Auditable Logs, DER Resources, AI Decisions, Events, History and AI Agent on a consistent card grid.

  • Three themes show token thinking (navy and sand, slate, cream), and the sun/moon toggle makes theming a feature rather than an afterthought.

  • Every panel has an icon and a text heading; 'Resolved' chips carry a text label, so status is not colour-only.

  • Explainability is designed in: each AI decision has a written rationale next to it, and the log shows request and confirm events.

  • Housekeeping to do: the Figma file title currently reads 'Health Mobile Application Prototype (Community)'. Rename it before sharing the link so no reviewer wonders whether it started from a template.

3. Problem, solution and benefit

3.1 Problem

Great Britain's electricity system is decarbonising and decentralising. NESO reports that distributed and consumer energy resources (batteries, small-scale generation, electric vehicles and more) form a significant and growing share of capacity, yet the system operator currently has limited visibility of them and can access services from only a small subset. This causes operability challenges and higher balancing costs.

For a DSO control room the problem shows up as overloads on individual feeders, many tools to check, unclear reasons for automated recommendations, and a heavy audit burden. Operators need to see the network, understand any recommended action and trust that everything is recorded.

3.2 Solution

A single command centre. The header summarises agent status, latency, number of audit logs, calls made and AI decisions. Feeder cards show load against capacity. When an overload occurs an event is created, the AI agent evaluates available DER, and its decision and reasoning appear in the AI Decisions panel. The operator approves or overrides; approved dispatches go out as Beckn-style init and confirm messages and are written to the Auditable Logs. History keeps past readings and yearly consumption, and the AI Agent panel answers questions in natural language.

3.3 Benefit

  • Faster detection and response: overloads, DER availability and recommendations sit on one screen.

  • Trust through explainability: every AI decision shows its reason and can be overridden.

  • Compliance: an auditable, time-stamped record of who or what did what.

  • Less context switching, which reduces operator error.

  • Themes for different lighting: dark and slate for night shifts, cream for day.

  • Supports flexibility markets by making DER dispatch visible and repeatable.

11. Technical documentation

11.1 Architecture and recommended stack

A React and TypeScript front end receives live updates over WebSockets or server-sent events from a Python (FastAPI) back end. Readings are stored in a time-series capable database. An agent service watches readings, creates events and proposes decisions using rules first and an LLM for explanation. A safety layer enforces limits and requires human approval. A Beckn adapter sends init and confirm messages for DER flexibility. Every action is written to an append-only, hash-chained audit table.

11.4 Software development life cycle (SDLC) recommendation

Recommended model: Hybrid: Agile delivery (two-week iterations) wrapped in V-model style verification and validation gates, with a simulation-first, staged rollout (shadow mode, then advisory, then supervised control).

Why this model fits

  • This is safety-related, regulated infrastructure software, so requirements traceability, formal test evidence and sign-off gates matter more than in a consumer app.

  • The AI and UI still need rapid feedback from operators, so iterations remain short.

  • Simulation-first testing lets the team prove behaviour without touching real equipment.

  • Staged rollout limits risk: the system first observes, then advises, then acts under supervision.

  • Auditability requires traceable links from requirement to test to release.

12. Design system

12.1 Colour theory

The palette is built on cool navy (#162D57) and slate (#364152, #8794A6), which communicate authority, calm and reliability for long shifts. Sand (#D1C7A9) is a warm neutral that sits opposite blue on the colour wheel, giving the navy theme a complementary lift without harsh contrast. Signal yellow (#FED65D) is reserved for attention and primary actions, and green (#15A34A) for 'resolved' and healthy states.

Colour has a job: blue for structure, yellow for what needs attention, green for good news. In a control room this semantic discipline matters more than decoration, and each colour meaning must also be carried by an icon or word.

Three themes are provided. Navy and sand is the signature look; slate is a lower-glare dark option for night shifts; cream is a light option for bright rooms. Because they share the same roles, they can be built as three token sets.

12.4 Typography

The design uses one bold humanist sans-serif. For a data-dense tool I recommend a two-family system: a neutral UI sans (for example Inter) with tabular numerals for values, and a monospace (for example JetBrains Mono or IBM Plex Mono) for IDs and log lines, so characters such as 0 and O or 1 and l are never confused.

12.5 Styling strategies

  • Semantic colour tokens (status-ok, status-warning, status-critical, surface, text-primary) so three themes share one component set.

  • Redundant encoding: every status uses icon, word and colour together.

  • Progressive disclosure: summary cards on the main screen, full detail on open (for example, JSON payload on demand).

  • Consistent card grid with equal gutters and one panel-header style.

  • Alarm hierarchy: at most two severity colours plus text, so alarms are not lost in decoration.

  • Calm defaults for long shifts: no gratuitous animation, reduced-motion support, dark theme option.

12.6 Design structure and layout

  • Top row: KPI strip and theme toggle. Middle: Feeder, Auditable Logs, DER Resources and AI Decisions as four columns. Bottom: Events and History, with the AI Agent chat.

  • Reading order follows the incident: status, load, log, resources, decision, event, history.

  • Panels scroll independently with visible scrollbars and keyboard focus.

  • Responsive plan: desktop control-room first; tablet for supervisors; panels stack in the same order.

12.7 Components, iconography and imagery

  • Icons: one outline family for panel headings and toggles, always with a text label.

  • Chips: 'Resolved' and severity chips with icon plus text.

  • Progress bars: feeder load bars with numeric value at the end.

  • Imagery: none needed; data visualisation only. Use text alternatives for any charts.


13. WCAG 2.2 accessibility audit

Short answer: not yet compliant, and static designs cannot be certified. For a control-room tool the issues that matter most are text size and contrast, live-updating content, and keyboard access to scrollable panels.

Likely fails are secondary grey text on navy and slate, and white text on the green 'Resolved' chip. WCAG 2.2.2 (Pause, Stop, Hide) is a real risk because live feeds update continuously.

Target: WCAG 2.2 Level AA (the current W3C Recommendation since 5 October 2023). Statuses: Likely pass, Needs test, Likely fail (fix), Not verifiable in a static design.

14. Visual appeal evaluation and fix list

Overall visual appeal: 6.5 out of 10

This looks like serious operations software and the navy and sand theme is distinctive. The structure is strong. The design is held back by very small text, low-contrast secondary information and a dense grid that gives everything equal weight.

For this domain the goal is not decoration but calm legibility. Larger key values, fewer simultaneous colours and a clear alarm hierarchy would move it to an 8 without losing any features.

What works

  • Credible control-room palette with three themes

  • Clear panel roles and reading order

  • Explainable AI decisions built into the layout

  • Domain-accurate concepts (feeders, DER, dispatch, audit)
